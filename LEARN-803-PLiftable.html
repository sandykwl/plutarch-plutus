01

The five-minute primer

Only what you need for this issue — not a full Plutarch tour.

Plutarch is an eDSL embedded in Haskell that compiles down to UPLC (Untyped Plutus Core), the low-level language that actually runs on Cardano. You write ordinary Haskell that builds a Plutarch program; then you compile or evaluate that program separately. Four ideas carry the whole issue.

1–2. The P prefix, and the odd kind

Plutarch's own types are prefixed with P: PInteger, PBool, PMaybe, PEither, PPair, PRational. They don't have kind Type the way ordinary Haskell types do — they have kind S -> Type. S is a phantom “scope” tag, playing exactly the role that s plays in ST s a: you thread it through, you rarely construct it yourself.

3. Term s a is a program fragment, not a value

A value of Plutarch-type a is written Term s a: a piece of Plutarch code — an AST — that, once compiled and run, produces a value of type a. Read it as “quoted code”, not “a plain value”.

Term a program fragment — compiled UPLC code, not a Haskell value
s phantom scope tag — same role as s in ST s a
PInteger the on-chain integer type — not Haskell's Integer

4. The Haskell ↔ Plutarch bridge

Because PInteger ≠ Integer, something has to convert between the two worlds. That bridge is exactly what issue #803 is about testing:

Haskell value pconstant→ Term s a evaluate→ UPLC plift→ Haskell value

That's the whole primer. You don't need compilation internals, Scott encoding, or Data encoding to do this issue — just this bridge.

02

What PLiftable guarantees

Defined in Plutarch/Internal/Lift.hs:

Plutarch/Internal/Lift.hs · ~line 164
class PlutusType a => PLiftable (a :: S -> Type) where
  type AsHaskell a  :: Type   -- the everyday Haskell mirror of `a`
  type PlutusRepr a :: Type   -- an intermediate "Plutus universe" form

  haskToRepr :: AsHaskell a  -> PlutusRepr a
  reprToHask :: PlutusRepr a -> Either LiftError (AsHaskell a)
  reprToPlut :: forall s. PlutusRepr a -> PLifted s a
  plutToRepr :: (forall s. PLifted s a) -> Either LiftError (PlutusRepr a)

AsHaskell a is the everyday type paired with Plutarch type a:

Plutarch type aAsHaskell a
PIntegerInteger
PMaybe PIntegerMaybe Integer
PEither a bEither (AsHaskell a) (AsHaskell b)
PRationalPlutusTx.Rational
PBuiltinPair a b(AsHaskell a, AsHaskell b)

PlutusRepr a is plumbing: builtin containers like PBuiltinList and PBuiltinPair can only hold a fixed set of “universe” types, so some conversions need an intermediate hop. Treat it as an implementation detail for this issue.

The two laws

Everything below is one commuting diagram. Read each hop as “convert, then convert back, and you're where you started”:

pconstant
AsHaskell a
the Haskell value you write
→ haskToRepr ← reprToHask (Either)
PlutusRepr a
Plutus‑universe encoding
→ reprToPlut ← plutToRepr (Either)
Term s a
the on‑chain term
plift

The two per-hop round trips are the class's actual laws; the full left-to-right and right-to-left trips are pconstant and plift.

Law 1 reprToHask ∘ haskToRepr = Right
Law 2 plutToRepr ∘ reprToPlut = Right
Implies plift ∘ pconstant = id

Derivations via DeriveBuiltinPLiftable, DeriveDataPLiftable, and DeriveNewtypePLiftable satisfy these laws automatically. A hand-written instance might not — which is exactly what these tests catch.

03

The test harness: checkPLiftableLaws

A ready-made property-test bundle in plutarch-testlib that turns the diagram above into three QuickCheck properties.

plutarch-testlib/Plutarch/Test/Laws.hs · ~line 298
checkPLiftableLaws ::
  forall (a :: S -> Type).
  ( Arbitrary (AsHaskell a)
  , Pretty    (AsHaskell a)
  , Eq        (AsHaskell a)
  , Show      (AsHaskell a)
  , PLiftable a
  ) =>
  [TestTree]
checkPLiftableLaws =
  [ testProperty "plutToRepr . reprToPlut = Right" ...
  , testProperty "reprToHask . haskToRepr = Right" ...
  , testProperty "plift . pconstant = id"          ...
  ]

You call it at the type level: checkPLiftableLaws @(PEither PInteger PInteger). It returns [TestTree] (plain tasty tests) to drop into a testGroup. QuickCheck generates random AsHaskell a values via Arbitrary — which is exactly why AsHaskell a needs Arbitrary, Pretty, Eq, and Show. Remember that constraint list; it's where the real work in this issue hides.

The existing, working usage to copy:

plutarch-testlib/test/Plutarch/Test/Suite/Plutarch/Maybe.hs
testGroup (instanceOfType @(S -> Type) @(PMaybe PInteger) "PLiftable") $
  checkPLiftableLaws @(PMaybe PInteger)
04

Where the gap actually is

Cross-referencing the suite directory against every checkPLiftableLaws / checkLedgerProperties call site:

TypeStatusNote
PMaybe / PMaybeData Covered Tested directly in Maybe.hs.
PFoo (DeriveAsTag) Covered Exercised in DeriveAsTag.hs, incl. the local pattern for supplying instances.
PRawValue, PMap, PEitherData Covered Via checkLedgerProperties, which calls checkPLiftableLaws internally.
PEither Target Only the Data variant (PEitherData) is tested; plain PEither isn't.
PRational Target No Arbitrary/Pretty for PlutusTx.Rational yet, in Rational.hs.
PPair Target Pair.hs has only golden tests. A PLiftable instance was not found — verify before committing to it.
PBuiltinPair Fallback Confirmed PLiftable instance exists already — safer starting point if PPair lacks one.

Confirm this yourself before starting — grep -rn "checkPLiftableLaws\|checkLedgerProperties" plutarch-testlib/test.

05

The fix, step by step

The mechanical 90%

For each target type, add one group to its suite file — the same shape as Maybe.hs:

e.g. plutarch-testlib/test/Plutarch/Test/Suite/Plutarch/Either.hs
, testGroup (instanceOfType @(S -> Type) @(PEither PInteger PByteString) "PLiftable") $
    checkPLiftableLaws @(PEither PInteger PByteString)

Pick monomorphic element types (PInteger, PBool, PByteString, PString) so the constraints resolve cleanly.

The real 10%: the missing instances

checkPLiftableLaws @a needs Arbitrary, Pretty, Eq, Show on AsHaskell a. Eq/Show almost always already exist. The two that bite:

  • AsHaskell (PEither PInteger PByteString) = Either Integer ByteString. QuickCheck ships Arbitrary (Either a b), but Prettyprinter has no Pretty (Either a b) — you add it.
  • AsHaskell PRational = PlutusTx.Rational. You likely need both an Arbitrary and a Pretty instance.

This is exactly why the issue says these types “have been skipped” — the testGroup line is trivial; the instance plumbing is the actual task.

Follow the existing convention for where instances live — DeriveAsTag.hs shows the local pattern, instances defined right next to the test:

plutarch-testlib/test/Plutarch/Test/Suite/Plutarch/DeriveAsTag.hs
instance Pretty (PFoo s) where
  pretty = pretty . show

instance Arbitrary (PFoo s) where
  arbitrary = elements [A, B, C, D, E]

Reusable orphans (like Pretty (Either a b)) belong in the shared home instead: plutarch-testlib/Plutarch/Test/QuickCheck.hs (see the deriving newtype instance Pretty ... block, ~line 184).

Watch out

Plutarch/Pair.hs derives PlutusType via DeriveAsSOPStruct, but no PLiftable instance turned up in a search of that file. Check first: grep -n "PLiftable" Plutarch/Pair.hs. If it's missing, either add the appropriate deriving ... PLiftable line (a slightly bigger, library-side change — call it out in the PR) or start with PBuiltinPair instead, which already has one, and note PPair as follow-up. Prefer the smallest correct change.

Tip

Compile errors are your friend here — a missing constraint surfaces as No instance for (Arbitrary ...) / (Pretty ...), telling you precisely what to add next.

06

Build & run

shell
nix develop          # first run downloads a lot; pins GHC 9.8.4 + native deps
cabal build all
cabal test plutarch-testlib

Iterate faster by filtering to your new group (tasty pattern match):

shell
cabal test plutarch-testlib --test-options='--pattern "PLiftable"'

Pure law tests shouldn't touch golden output, but if a golden diff ever appears and the change is intentional: cabal test plutarch-testlib --test-options='--accept'.

07

Suggested order of attack

Smallest, most certain wins first — each type is an independent, compiler-guided change, good for small reviewable commits.

  1. PEither PInteger PByteString Quick win

    In Either.hs: add the testGroup line; supply Pretty (Either a b) — Arbitrary already exists.

  2. PRational Core case

    In Rational.hs: add Arbitrary and Pretty for PlutusTx.Rational, then the testGroup line.

  3. PBuiltinPair (or PPair) Check first

    In Pair.hs: confirm whether PPair has a PLiftable instance before committing to it; fall back to PBuiltinPair if not.

  4. Anything else uncovered Sweep

    Grep for other types with a PLiftable instance but no law coverage; add them the same way.
