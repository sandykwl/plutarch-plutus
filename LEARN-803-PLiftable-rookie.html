01

The world this code lives in

Cardano is a blockchain — picture a shared ledger copied across thousands of independent computers, all of which must independently agree on every transaction, with nobody in charge of the master copy. People write smart contracts — small programs enforcing rules like "only pay this out if condition Y is met" — that run as part of those transactions.

Plutarch is the tool this repository builds: a Haskell library for writing those smart contracts. It's an eDSL — the code you write looks like ordinary Haskell, uses Haskell's syntax and tooling, but it isn't directly executed the way a normal Haskell program is. Instead, it describes a separate program, which then gets compiled down to UPLC, the actual low-level bytecode the blockchain runs:

Your Plutarch code
(looks like Haskell) compiles to→ UPLC
(on-chain bytecode) runs on→ Cardano
(thousands of computers re-check the result)
Why this matters for issue #803

Smart contracts often move real money or real assets, and blockchain transactions are very hard (often impossible) to undo once confirmed. A subtle bug that a normal app could patch tomorrow can, here, mean an unrecoverable loss today. That's why this codebase leans so heavily on formal laws (rules a piece of code must always satisfy) and automated tests that check those laws relentlessly, instead of just trusting a human read-through. Issue #803 is about extending exactly that safety net.

02

A Haskell-flavored primer, from zero

In Haskell, every value has a type: a label telling you (and the compiler) what kind of thing it is. For example, the number 5 has type Int — written 5 :: Int, read aloud as "5, of type Int." This lets the compiler catch a whole category of mistakes — like trying to add a number to a piece of text — before the program ever runs.

Plutarch's own types are prefixed with a capital P: PInteger, PBool, PMaybe, PEither, PPair, PRational. That prefix is your visual cue: "this is a Plutarch (on-chain) type, not a plain Haskell one."

These types have an unusual shape. An ordinary Haskell type just is a type. A Plutarch type like PInteger is a little factory that, given a phantom "scope" tag conventionally called s, produces a type. You'll see this written as kind S -> Type — don't worry about the word "kind" beyond "a type for types." The s/S pattern plays exactly the role that s plays in Haskell's ST s a, if you've seen that before; if not, just know: you thread it through, you almost never build it yourself.

The single most important idea: Term s a is not a value

A value of Plutarch-type a is written Term s a. Read Term as "a fragment of program", not "a value sitting in memory." It's more like a quoted piece of code — an instruction that, once compiled and actually run, produces a value of type a. This trips up almost everyone on their first day with Plutarch, so here's the whole type broken into pieces:

Term a program fragment — compiled code, not a Haskell value sitting in memory
s the phantom scope tag mentioned above — carry it, don't build it
PInteger the on-chain integer type — not the same thing as Haskell's own Integer

The bridge between the two worlds

Because PInteger and Haskell's Integer are genuinely different things, something has to convert between them. Two functions do that conversion, and they're exactly what issue #803 is about putting to the test:

  • pconstant — takes an everyday Haskell value and lifts it into a Plutarch term.
  • plift — takes a finished Plutarch term and evaluates it back out to a Haskell value.
Haskell value pconstant→ Term s a evaluate→ UPLC plift→ Haskell value

That's genuinely the whole primer. You do not need to understand compilation internals, or the deeper encoding tricks Plutarch uses, to do this issue — just this bridge, and the class that powers it, coming up next.

03

What PLiftable promises

Think of translating a document from English to French and back to English. If the translation is faithful, you should land back on your original English text, word for word. PLiftable is exactly that round-trip promise, formalized for the Haskell ↔ Plutarch bridge. It's defined in Plutarch/Internal/Lift.hs:

Plutarch/Internal/Lift.hs · ~line 164
class PlutusType a => PLiftable (a :: S -> Type) where
  type AsHaskell a  :: Type   -- the everyday Haskell mirror of `a`
  type PlutusRepr a :: Type   -- an intermediate "Plutus universe" form

  haskToRepr :: AsHaskell a  -> PlutusRepr a
  reprToHask :: PlutusRepr a -> Either LiftError (AsHaskell a)
  reprToPlut :: forall s. PlutusRepr a -> PLifted s a
  plutToRepr :: (forall s. PLifted s a) -> Either LiftError (PlutusRepr a)

AsHaskell a is the everyday type standing in for Plutarch type a. A few examples, so the pattern clicks:

Plutarch type aAsHaskell a
PIntegerInteger
PMaybe PIntegerMaybe Integer
PEither a bEither (AsHaskell a) (AsHaskell b)
PRationalPlutusTx.Rational

PlutusRepr a is an intermediate stopover needed because some of Plutarch's low-level containers can only hold a fixed set of "universe" types. For this issue, treat it as plumbing you don't need to redesign — just something the round trip passes through.

The laws, in plain English first

Everything below is one continuous round trip. Each arrow is a conversion; each law says "go one way, then the other, and you're back where you started":

pconstant
AsHaskell a
the Haskell value you write
→ haskToRepr ← reprToHask (Either)
PlutusRepr a
Plutus‑universe encoding
→ reprToPlut ← plutToRepr (Either)
Term s a
the on‑chain term
plift

The two short round trips are the class's actual laws; the full trip from end to end is pconstant (left→right) and plift (right→left).

In plain English: encode a Haskell value into its Plutus-universe representation, then decode it straight back — you should get the exact value you started with. That's Law 1.

Law 1reprToHask ∘ haskToRepr = Right

In plain English: lift a representation into an on-chain term, then evaluate that term straight back — same story. That's Law 2.

Law 2plutToRepr ∘ reprToPlut = Right

Put both hops together and you get the headline guarantee: encode a Haskell value all the way into an on-chain term, evaluate it back, and you get exactly what you put in.

Impliesplift ∘ pconstant = id

Instances built with the standard helpers — DeriveBuiltinPLiftable, DeriveDataPLiftable, DeriveNewtypePLiftable — satisfy these laws automatically. A hand-written instance might not. That gap is exactly what tests catch.

04

How computers check this automatically

If you haven't written automated tests before, here's the short version, because it matters for understanding why this issue exists at all.

Unit test

You write a specific example by hand: input, and the exact output you expect. Great for pinning down known edge cases, but you only ever check what you thought to write down.

reverse [1,2,3] == [3,2,1]

Property-based test

You state a general rule instead of one example, and a tool (here, QuickCheck) throws hundreds of random inputs at it, hunting for any case that breaks the rule.

reverse (reverse xs) == xs -- checked for ~hundreds of -- random xs, automatically

Because it's automatic and random, a property test is far more likely to catch a subtle round-trip bug than a handful of examples a human thought to write. This project has a ready-made property-test bundle, in plutarch-testlib/Plutarch/Test/Laws.hs, that turns the PLiftable laws from the last section directly into checkable properties:

plutarch-testlib/Plutarch/Test/Laws.hs · ~line 298
checkPLiftableLaws ::
  forall (a :: S -> Type).
  ( Arbitrary (AsHaskell a)
  , Pretty    (AsHaskell a)
  , Eq        (AsHaskell a)
  , Show      (AsHaskell a)
  , PLiftable a
  ) =>
  [TestTree]
checkPLiftableLaws =
  [ testProperty "plutToRepr . reprToPlut = Right" ...
  , testProperty "reprToHask . haskToRepr = Right" ...
  , testProperty "plift . pconstant = id"          ...
  ]
What's that @(...) syntax?

You call this function at the type level: checkPLiftableLaws @(PMaybe PInteger). The @ is called a type application — it's how you tell the compiler exactly which type to plug in, the same way a normal function argument tells it which value to plug in. Nothing more mysterious than that.

Here's that call in its natural habitat, the existing test for PMaybe:

plutarch-testlib/test/Plutarch/Test/Suite/Plutarch/Maybe.hs
testGroup (instanceOfType @(S -> Type) @(PMaybe PInteger) "PLiftable") $
  checkPLiftableLaws @(PMaybe PInteger)

Notice that checkPLiftableLaws needs Arbitrary, Pretty, Eq, and Show for AsHaskell a — that's how QuickCheck knows how to generate random values, print them when a test fails, and compare them. Hold onto that list; it's exactly where the real work in this issue lives, in section 06.

06

The fix, step by step

The easy 90%

For each target type, you add one small group to its test file — the exact same shape as the Maybe.hs example above:

e.g. plutarch-testlib/test/Plutarch/Test/Suite/Plutarch/Either.hs
, testGroup (instanceOfType @(S -> Type) @(PEither PInteger PByteString) "PLiftable") $
    checkPLiftableLaws @(PEither PInteger PByteString)

Pick concrete, simple element types — PInteger, PBool, PByteString, PString — rather than something generic, so every constraint the function needs can actually be resolved.

The real 10%: the missing instances

Remember the constraint list from section 04: checkPLiftableLaws @a needs Arbitrary, Pretty, Eq, Show for AsHaskell a. Eq and Show almost always already exist. The two that don't:

  • AsHaskell (PEither PInteger PByteString) = Either Integer ByteString. QuickCheck already ships Arbitrary (Either a b), but the pretty-printing library has no Pretty (Either a b) — you write one.
  • AsHaskell PRational = PlutusTx.Rational. You'll likely need both an Arbitrary and a Pretty instance here.

This is exactly why the issue says these types have "been skipped" — the test line itself is trivial; supplying these instances is the actual task.

Wait, what's an "instance", concretely?

Recall from the glossary: an instance is the real code fulfilling a typeclass's promise for one type — e.g. "here's exactly how to print an Either Integer ByteString nicely, satisfying the Pretty typeclass." You'd normally write that instance next to the typeclass's own definition, or next to the type's own definition. Here you own neither — Either and Pretty both come from other libraries — so what you write is called an orphan instance. Haskell allows this (with a mild warning), and it's already the accepted pattern throughout this test library. Nothing to worry about.

Follow the existing convention for where to put these instances — DeriveAsTag.hs shows the local pattern, defined right beside the test that needs them:

plutarch-testlib/test/Plutarch/Test/Suite/Plutarch/DeriveAsTag.hs
instance Pretty (PFoo s) where
  pretty = pretty . show

instance Arbitrary (PFoo s) where
  arbitrary = elements [A, B, C, D, E]

If an instance is reusable across multiple test files (like Pretty (Either a b) probably is), put it in the shared home instead: plutarch-testlib/Plutarch/Test/QuickCheck.hs (see the deriving newtype instance Pretty ... block, around line 184).

Watch out

Plutarch/Pair.hs derives PlutusType via DeriveAsSOPStruct, but no PLiftable instance turned up when searching that file. Check first: grep -n "PLiftable" Plutarch/Pair.hs. If it really is missing, either add the appropriate deriving ... PLiftable line yourself (a bigger, library-side change worth flagging in your PR description) or start with PBuiltinPair instead, which already has one, and note PPair as a follow-up. Prefer the smallest change that's still correct.

A reassurance for your first compiler errors

When you're missing an instance, GHC (the Haskell compiler) will say something like No instance for (Pretty (Either Integer ByteString)). Read that as a precise to-do item, not a failure: it's telling you the exact type and exact typeclass you still need to satisfy. Compiler errors in Haskell are usually this specific — treat them as directions, not scolding.

07

Build & run

Two tools do the heavy lifting here, and it's worth knowing what each is for before you type the commands:

  • Nix builds an identical, reproducible toolbox on your machine — the right compiler version, the right supporting libraries — so "it works on my machine but not yours" stops being a problem.
  • Cabal is Haskell's build tool. Once the toolbox exists, Cabal is what actually compiles your code and runs the tests.
shell
nix develop          # first run downloads a lot; pins GHC 9.8.4 + native deps
cabal build all
cabal test plutarch-testlib

While you're iterating, filter down to just the group you added (tasty's pattern match), so you're not waiting on the whole suite every time:

shell
cabal test plutarch-testlib --test-options='--pattern "PLiftable"'

Pure law tests like these shouldn't touch any golden (reference-file) output. If a golden diff ever does appear and the change is genuinely intentional: cabal test plutarch-testlib --test-options='--accept'.

08

Suggested order of attack

Start with the smallest, most certain win, then build confidence from there. Each type below is an independent, compiler-guided change — good for small, reviewable commits rather than one giant one.

  1. PEither PInteger PByteStringQuick win

    In Either.hs: add the testGroup line; supply Pretty (Either a b) — Arbitrary already exists.

  2. PRationalCore case

    In Rational.hs: add both Arbitrary and Pretty for PlutusTx.Rational, then the testGroup line.

  3. PBuiltinPair (or PPair)Check first

    In Pair.hs: confirm whether PPair actually has a PLiftable instance before committing to it; fall back to PBuiltinPair if it doesn't.

  4. Anything else uncoveredSweep

    Grep for other types that have a PLiftable instance but no law coverage yet, and add them the same way.

10

Turning this into a real pull request

If you've never contributed to an open-source project before, here's the standard shape that this whole process follows, end to end:

  1. Fork the repo

    Make your own copy of the repository on GitHub (skip this if you already have push access and can branch directly).

  2. Clone it to your machine

    git clone <your-fork-url> — downloads the code so you can edit it locally.

  3. Create a branch for this change

    git checkout -b fix/803-liftable-coverage — keeps your work separate from the main line of development until it's reviewed.

  4. Make the edits from section 06

    Add the missing instances and testGroup lines, running the build/test commands from section 07 until everything is green.

  5. Commit with a clear message

    Explain why, not just what — e.g. "Add PLiftable law coverage for PEither, PRational, PPair (#803)."

  6. Push and open the pull request

    git push, then open a PR against the upstream repo. Reference "Fixes #803" (or "Contributes to #803") in the description so GitHub links it automatically.

  7. Expect review — and that's a good thing

    A maintainer will read your change and may ask for adjustments. That's the normal, healthy shape of the process, not a rejection of you or your work.

Everyone doing this work today once stared at S -> Type, or their first "No instance for..." error, and felt exactly the way you might feel right now. That feeling is not a sign you're in the wrong place.

This fix is small, compiler-guided, and entirely within reach as a first contribution — that's precisely why it landed on the easy list in the first place.
